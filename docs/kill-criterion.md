# Kill criterion (pre-registered, binding)

Committed before any strategy is tested. It must not be edited after seeing any strategy result. If it must change, add a dated amendment at the bottom that states the reason and was written before the affected test is run. Never rewrite the original text.

Written: 2026-11-01. No strategy has been run. No collected data exists yet.

## 1. Definitions

- `r` = (payout - stake) / stake, taken from real `proposal` responses for the exact contract (symbol, type, duration) being tested. Never hard-coded. Where payouts vary, use the mean `r` observed, and also test at `r - 0.05` (sensitivity).
- `p_be = 1 / (1 + r)`, the break-even win probability.
- A "trade" is one simulated or real contract from entry to expiry. Trades are independent for counting only if non-overlapping: a strategy may not open a new contract on a symbol while a previous one on that symbol is still open. The backtester enforces this, so n is the count of non-overlapping trades.
- `K` = the total number of strategy variants (strategy x parameter set x contract x symbol) ever evaluated against the validation or holdout data in this project. Every evaluated variant is counted, including discarded ones. The count is stored in the repo and only increases.
- Splits are time-ordered. The holdout is the most recent block of collected data, fixed by a hash recorded in `docs/gates.md` before any strategy is evaluated, and touched once per final candidate. Each opening is logged.

## 2. Pass conditions

A strategy variant passes the edge gate only if ALL of these hold on the locked holdout, and then again on forward demo trading:

1. Sample size: the number of non-overlapping trades `n >= n_min`.
2. Significance: the one-sided Wilson lower confidence bound of the win rate, at confidence `1 - 0.05 / K` (Bonferroni over K variants), is strictly greater than `p_be`. Additionally the exact one-sided binomial test of `H0: p <= p_be` must reject at the Holm-adjusted level over the same K variants. Both must hold.
3. Expectancy: expectancy per unit stake `E = p_hat * r - (1 - p_hat)` is positive using the real `r`, and still positive at `r - 0.05`.
4. Drawdown: maximum drawdown on the holdout is within the risk specification (HANDBOOK 10). If the owner has not set it, condition 4 fails by default.
5. Regimes: the holdout is split into at least two contiguous time blocks of equal trade count. In each block `E > 0`. If the holdout cannot be split into two blocks that each have at least `n_min / 4` trades, condition 5 fails.

## 3. n_min (power calculation)

For testing `H0: p = p_be` against `H1: p = p_be + delta`, one-sided, with alpha and power fixed below:

```
n_min = ceil( ( z_alpha * sqrt(p0*(1-p0)) + z_beta * sqrt(p1*(1-p1)) )^2 / delta^2 )
p0 = p_be, p1 = p_be + delta
```

Fixed parameters:

- `delta = 0.02` (2 percentage points above break-even). A smaller true edge is not worth chasing at the sample sizes we can collect.
- `alpha = 0.05 / K` for the holdout test (family-wise 0.05), `power = 0.80` (`z_beta = 0.8416`).
- For planning before K is known, the table below uses K = 1 and K = 20. The binding `n_min` is recomputed with the real `p_be` and the real K at Gate 1 and committed before the holdout is opened.

Planning values for r from 0.80 to 0.95 are generated by `derivbot.stats.edge.required_n` via `make power-table` and committed in `docs/power-table.md`. They are generated by code, not typed here, so they cannot be mistyped. They are for planning only.

If the achievable number of non-overlapping holdout trades is below `n_min`, the correct outcome is "cannot conclude", which is treated as a fail for going live. It is never a pass.

## 4. Control experiment (must pass before any real result is read)

Run the whole pipeline (data load, signal, backtest, gate) on at least 1,000 independent random series, both shuffled-return versions of real ticks and simulated random walks. The fraction of series for which any variant passes the gate must be at most `0.05 + 3 * sqrt(0.05 * 0.95 / 1000)` (about 0.0995). If it is higher, the harness is broken: fix it and rerun before reading any real result. The look-ahead canary (a deliberately cheating strategy) must be flagged by the harness.

## 5. Outcomes

- If no variant passes: the project stops before live readiness. A documented "no edge" is a successful outcome. Record it plainly in `docs/gates.md`.
- If a variant passes: it moves to forward demo trading, which must meet the same conditions 2 and 3 on fresh data, plus Gate 2 (demo matches backtest).
- Passing does not authorise real trading. Real trading is the owner's decision under HANDBOOK 11.4.

## 6. Things that do not count

Results from the old bot, `backtest_results.json`, or any run after the holdout was opened for exploring. In-sample or validation results as evidence of edge. Any result produced with a hard-coded `r`.

### A1.5 The tests, their count, alpha, correction and minimum samples

Null hypothesis for every test: eligible digits are independent and uniform on 0 to 9. P-values are upper tails of the stated reference distribution (two-sided for the runs test). Four tests, applied per symbol:

1. `uniformity_chi2`: Pearson chi-square on the ten digit counts, expected N/10 each, df = 9.
2. `parity_runs`: Wald-Wolfowitz runs test on the even/odd sequence (even = digit in 0,2,4,6,8), computed per segment and combined: z = (sum of runs - sum of E) / sqrt(sum of Var), with per segment E = 1 + 2*n1*n2/n and Var = 2*n1*n2*(2*n1*n2 - n) / (n^2 * (n-1)). Segments shorter than 10 ticks are dropped. Standard normal reference, two-sided.
3. `autocorrelation_portmanteau_10`: with x the digit value, m the mean of used digits, D = sum of (x - m)^2, and for lags k = 1 to 10 the within-segment pairs only: r_k = (C_k / P_k) / (D / N) where C_k is the sum of (x_t - m)(x_(t+k) - m) over within-segment pairs and P_k their number. Q = sum over k of P_k * r_k^2, chi-square reference with df = 10.
4. `pair_independence_chi2`: within each segment take non-overlapping pairs (d1,d2), (d3,d4), ... Build the 10 x 10 table of (first, second). Pearson chi-square of independence, df = 81. Non-overlapping pairs are used on purpose, because overlapping pairs reuse digits and break the reference distribution.

Counts: 4 tests x 2 confirmatory symbols = 8 confirmatory tests (family size 8). 4 tests x 6 exploratory symbols = 24 exploratory tests (family size 24, a separate family). 32 tests in total.

Error control: family-wise alpha = 0.05 per family, Holm step-down correction over the family. Holm is used because it is valid under any dependence between the tests. A test that cannot run (below its minimum, see below) counts as not rejected and the family size stays 8 (or 24).

Minimum sample sizes (valid digits or pairs after segmenting): uniformity 10,000; runs 10,000; portmanteau 10,000 pairs at every lag 1 to 10; pair independence 20,000 digits (10,000 pairs). Gate 1 additionally requires at least 100,000 eligible ticks for each confirmatory symbol (about 1.2 days of 1HZ100V and 2.3 days of R_100 at the nominal rate); exploratory symbols need 20,000. A confirmatory symbol below its minimum makes the Gate 1 outcome "cannot conclude", never a pass.

Why 100,000: docs/power-gate1.md shows a parity bias large enough to beat break-even at stake 1.00 (P(even) = 0.512821) needs about 19,448 digits for 80% power at alpha 0.05/8, two-sided; at the minimum stake (0.530303) about 3,479. 100,000 is more than five times the harder of the two.

### A1.7 Decision rule for Gate 1

Let the confirmatory family be the 8 p-values from the run.

- Structure found requires all three: (i) at least one confirmatory test rejects under Holm at 0.05; (ii) for the rejecting symbol and test, the eligible ticks split in time order into two halves of equal tick count each give an unadjusted p < 0.05 for the same test; (iii) the run is valid (below).
- Inconclusive: (i) holds but (ii) fails. No strategy work. More data may be collected only under a new amendment, and only ticks after that amendment count.
- No structure detected: no confirmatory test rejects. This is a recorded negative result and a successful outcome of the research. No strategy work. The project does not proceed to Gate 1b unless the owner writes a new amendment first.
- Cannot conclude: a confirmatory symbol is below its minimum, or the run is invalid.
- Statistical structure is not an edge. A rejection says digits deviate from the null, not that any contract beats p_be. For any parity-related finding the run also reports P(even) with a 95% Wilson interval beside p_be at both stakes. Strategy work (a hypotheses file, then Gate 1b under v1 section 2) starts only after "Structure found" AND only on ticks collected after a further amendment.
- Exploratory results are printed in a separate table marked EXPLORATORY and are never used in this rule.

Run validity: the run includes 200 shuffled copies of each confirmatory symbol's digit sequence (shuffled within segments). For each of the 4 tests, the fraction of shuffled copies rejecting at unadjusted alpha 0.05 must lie within 0.05 +/- 3 x sqrt(0.05 x 0.95 / 200), that is [0.0038, 0.0962]. With 8 such checks, a chance failure of a correct harness is about 2% (8 x 0.0027); that small risk is accepted and a failure is treated as a harness fault. If any check is outside the band, the run is INVALID: its results are not reported as findings, the fault is fixed, and the run is repeated only under a new amendment on ticks collected after that amendment.

### A2.2 Maximum contiguous gap (the number and the reason)

Two ticks are contiguous if and only if their epochs differ by exactly the nominal interval: 1 second for 1HZ100V and 2 seconds for R_100. Any larger difference ends the segment. In other words the maximum gap that still counts as contiguous is zero missing ticks.

Reasons:

1. A missing tick turns an adjacent pair into a pair two steps apart. The serial tests (runs, autocorrelation, pair independence) are defined on consecutive ticks, and the hypotheses they probe (that one tick's digit carries information about the next) are about lag 1. Mixing lags changes what the statistic measures.
2. The data show no tolerance is needed. In the sample above, spacing is exactly nominal everywhere except at real outages, so a strict rule discards almost nothing.
3. Data are plentiful (about 86,400 ticks a day for 1HZ100V and 43,200 for R_100 at the nominal rate), so discarding pairs across outages costs little power.
4. A strict threshold cannot be tuned after seeing results, which a tolerance of "a few seconds" could be.

Exploratory symbols keep the A1 rule: a new segment starts when the epoch difference exceeds 60 seconds. Their tick spacing is irregular and adjacency is only loosely meaningful; their results stay exploratory.

### A2.3 Which tests need contiguous segments

- `uniformity_chi2` may use ALL eligible digits, regardless of segment boundaries and regardless of segment length. Uniformity of the marginal distribution does not depend on adjacency.
- `parity_runs`, `autocorrelation_portmanteau_10` and `pair_independence_chi2` run within contiguous segments ONLY. They use only segments with at least 10 ticks. Digits in shorter segments are used by the uniformity test only. For these three tests the digit mean m, the sum D and the count N in the A1.5 formulas are taken over the digits of the used segments only. No pair of ticks from different segments is ever used, and the pairs of `pair_independence_chi2` start at the first tick of each segment.
- The minimum sample sizes of A1.5 apply to the digits and pairs that remain after these rules.

### A2.4 Merging sources

Ticks may come from the streaming collector (source=stream) and from backfill (source=backfill), possibly from several database files. They are merged on (symbol, epoch). If the same (symbol, epoch) appears in two sources with the same quote it counts once. If the quotes differ, that tick is excluded from every test and the number of such ticks is reported (the check so far found 0 differences in 19 comparisons). Segments are formed on the merged series.

### A3.2 Defect 1: the shuffle validity rule of A1.7 cannot work for uniformity

A1.7 says that among 200 shuffled copies of each confirmatory sequence, every one of the 4 tests must reject at a rate inside [0.0038, 0.0962]. Its rejection rate is therefore either 0 or 1, never a sample from the null. As written, the rule would declare every run INVALID.

Correction, replacing the shuffled-copy check for that one test only:

- For the three serial tests (`parity_runs`, `autocorrelation_portmanteau_10`, `pair_independence_chi2`) nothing changes: 200 copies of the real sequence with digits shuffled within segments, rejection rate per test within 0.05 +/- 3 x sqrt(0.05 x 0.95 / 200), that is [0.0038, 0.0962].
- For `uniformity_chi2`, the check uses 200 SIMULATED series of independent uniform digits with exactly the same number of digits as the real eligible series of that symbol (the real digits are not used), rejection rate within the same band.

The number of validity checks stays 8 (4 tests x 2 confirmatory symbols), so the chance of a false INVALID for a correct harness stays about 2%. Nothing else in A1.7 changes.

### A3.3 Defect 2: quotes must carry exactly pip_size decimals before a digit is read

The digit rule of A1.4 is the last character of the quote formatted with exactly pip_size decimals. JSON numbers drop trailing zeros, so a quote of 1310.70 arrives as 1310.7. The collector stored the parsed value, so the last character of the stored text would be 7, not 0, for roughly one tick in ten. This was found by a test on 2026-10-31 and fixed in the commit titled "fix(store): restore trailing zeros to pip_size decimals and record pip_size per tick" (22:51Z). From that commit the store pads quotes with zeros to pip_size decimals (never rounds) and records pip_size per tick. Backfill rows were already stored with exactly pip_size decimals and are unaffected. No streamed tick after H0 had been stored by a collector before the fix, so no holdout tick is affected. The earlier local collector file is before H0 and excluded.

Rule added to A1.4: a tick is valid for digit analysis only if its stored quote has exactly pip_size decimals and its pip_size is recorded. Any other tick is excluded from every test and the number excluded, per symbol and source, is reported. A deployment must run code that includes the fix; a collector built from an earlier commit would write unusable digits.

### A5.4 The forward ledger (shadow outcomes), exact protocol

- Decision at tick t uses only ticks up to t. Entry spot is the quote of tick t+1. Exit spot is the quote of tick t+6 (5 ticks after entry). CALL wins if and only if exit is strictly above entry, PUT if and only if strictly below; a tie loses.
- A variant has at most one open shadow contract at a time. The next decision is at the exit tick or later. This is identical to derivbot.backtest.engine.run_backtest, and a test feeds the same simulated series to both and requires identical contracts.
- A shadow contract is DISCARDED, and counted as discarded, if any two consecutive ticks between t and t+6 differ in epoch by more than the nominal interval (1 second for 1HZ100V, 2 seconds for R_100, as in A2.2), or if the connection drops or the service restarts while it is open. Nothing else is dropped. No contract is added or removed after its outcome is known.
- Completed outcomes are stored append-only (table shadow_outcomes; updates and deletes are refused by the database).

### A5.5 The primary analysis (fixed now)

- r = 0.9009 (A5.1), so p_be = 1 / (1 + r) = 0.52607. Sensitivity uses r - 0.05 = 0.8509.
- n_min with delta = 0.02, power 0.80, alpha = 0.05 / 14, computed by derivbot.stats.edge.required_n, is 7,764. Each variant is evaluated EXACTLY ONCE, when it has N_EVAL = 7,800 completed shadow contracts. A variant that has not reached N_EVAL by 2026-12-31 is reported as inconclusive because of insufficient data. Nothing is decided on fewer contracts.
- A variant passes the forward test only if ALL hold, which are conditions 1, 2, 3 and 5 of section 2 of version 1 applied to the ledger: (1) n >= N_EVAL; (2) the one-sided Wilson lower bound of the win rate at confidence 1 - 0.05/14 is strictly above p_be AND the exact one-sided binomial test of H0: p <= p_be rejects at the Holm-adjusted level over the family of 14 (variants below N_EVAL enter the family with p = 1, so the family size is always 14); (3) expectancy per unit stake E = p_hat * r - (1 - p_hat) is positive at r = 0.9009 and at r - 0.05; (5) splitting the ledger in time order into two blocks of equal contract count, each block has E > 0 (each block holds at least N_EVAL / 4 contracts by construction). Condition 4 (drawdown) is not evaluated on a stakeless ledger and is reported for information only.
- No interim results. Before a variant reaches N_EVAL, only counts (completed, discarded) may be shown or discussed, and the reporting code refuses to print anything else. Peeking, early stopping, dropping a variant, or choosing among variants by their outcomes is forbidden.
- Control: if either control_random variant rejects H0 at its own evaluation, the harness is considered faulty and the whole evaluation is void until the fault is found and recorded.
- Meaning of a pass: a candidate edge on forward demo data only. It authorises nothing about real money. It would still need replication on a second forward window of equal size, consistency with the Gate 1 result, the independent reviews, and the owner's readiness checklist. Version 1 section 2 still applies in full to the locked holdout.
